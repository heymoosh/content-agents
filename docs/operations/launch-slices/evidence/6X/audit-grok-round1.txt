## Q2. Adoption of bytes that changed after approval? Stale / attacker / mistaken `--expect-fingerprint`?

**Yes, current bytes can be adopted. A stale hash cannot. A mistaken current hash can.**

Trace:

1. CLI fingerprints the file on disk now (`scripts/reconcile-approval-provenance.ts:59-70`).
2. `--write` requires `--expect-fingerprint` (`:79-80`).
3. `adoptApprovedQueueRow` recomputes inside the mutation lock and refuses a mismatch (`approval-provenance.ts:300-302`).

So:

- **Changed after markdown approval:** there is no approval-time hash for pre-journal rows. Adoption binds to **current** `{id, platform, format, asset, assetSha256}` (`approval-provenance.ts:92-101`). Preview shows mtime and the first five lines (`reconcile-approval-provenance.ts:62-64`); it does not compare against the original approved bytes.
- **Stale hash:** TOCTOU between preview and write is refused (`asset fingerprint changed`).
- **Wrong hash for different current bytes:** refused. The expected value is not a secret; it must equal the live composite.
- **Operator mistake:** copying the printed current hash without noticing a post-approval edit **will** adopt those bytes. That is coordinator trust, not an automatic bypass.
- **Attacker-chosen:** anyone who can run `--write` on a `content/` or `outreach/` folder can adopt any zero-event `approve` row by using the printed hash. Folder is constrained (`reconcile-approval-provenance.ts:42-49`). Direct journal writes would also work. This is not a remote forge of a different asset.

After adoption, scheduling still requires the live fingerprint to match the adopted one (`approval-provenance.ts:270-271`). A later edit blocks; it does not dispatch the old bytes.
