## Why this build, and why it can't be Atomize

Muxin wants to run a 14-day phased process (intro interview → Attention → Audience → Offer → Operations) to bootstrap a new solo venture — starting with a civic tech / Substack newsletter. Each phase composes original content from scratch (post ideas, lead magnet copy, landing page copy, a product outline, a price), guided by an interview and, later, real audience responses. That's fundamentally different from `/atomize`, whose entire job is extracting and trimming Muxin's own already-written sentences (CLAUDE.md rule 1) — there's no source essay to extract from here.

The repo already has the answer for "a build that composes instead of extracts": **Build 2, Fiction.** Its `stories/CLAUDE.md` wall states the same tension explicitly — composition is allowed *only because every output is reviewed and approved by Muxin before anything ships*, and it's walled off so the exception never bleeds into Builds 0/1. This build (call it Build 3 for now) is the same pattern applied to venture-building instead of serialized fiction: its own wall, its own consistency files, review-gated like everything else, and it hands finished, approved output to the *existing* publish mechanisms rather than building a second one.

### B. Consistency model — per-venture state files

Parallel to fiction's `bible.md` / `canon.md` / `characters/*.md`, one folder per venture (`venture/<slug>/`):

- **`intake.md`** — the answers to the 25-question intro interview (who it's for, proof, format, platform, time budget, what it shouldn't become) plus the Day 14 scorecard definition (see Model notes) fixed at kickoff, not invented after the fact. Written once, rarely changes.
- **`canon.md`** — append-only ledger of locked decisions as phases clear their checkpoints: chosen platform mix (+ why), the published Phase 1 posts (with live URLs), chosen lead magnet concept, the Phase 3 response-log AGGREGATE and a redacted synthesis (never raw quotes/identities — those stay in `responses.jsonl`, see below), chosen problem, transformation sentence, product outline, price. Never silently overwritten — but see Model notes for the idempotency gap in how fiction's own canon.ts does this, which this build should not copy as-is.
- **`state.md`** (or frontmatter fields on `canon.md` — open question, unchanged from original) — current phase number, checkpoint status, day tracking. Extend this to hold the editorial/delivery state split and checkpoint event IDs described in Model notes, not just a single "checkpoint pending/cleared" flag.
- **`responses.jsonl`** (new — kept OUT of git, same treatment as `data/analytics.db`) — the Phase 3 response log: one line per response with a stable id, source (survey/DM/comment/email), date, a hash of the respondent (never their raw name/email/handle), an eligibility flag against the target audience, either the exact quote or a redacted version, and an exclusion reason for anything that didn't count (duplicate, ineligible, unverifiable). `canon.md` only ever sees the aggregate count and a redacted synthesis once Phase 3's checkpoint clears.
- **`evidence-links.jsonl`** (round-3 — kept OUT of git, same treatment as `responses.jsonl`) — this venture's links into the **account-level** research-observation store, one line per linked observation, carrying only what is venture-relative: the derived `evidence_role` plus the basis that produced it, `unknown_ids`, `target_audience_fit`, and inclusion/exclusion. See `venture-schema-contract.md` §5.4b.
  - **The observations themselves are not in this folder.** They live once, account-wide, in a `research_observations` table inside the already-gitignored `data/analytics.db` — a metric pull, essay comment, Note reply, DM, email reply, subscriber move, follow-up question, or creator note, each carrying a keyed-HMAC respondent hash rather than raw identity where the source is identifying (`venture-schema-contract.md` §5.4a). Rounds 1–2 filed these per-venture as `phase1-observations.jsonl`; that was wrong, because the same body of audience evidence has to serve multiple ventures, the Signals room, and non-venture strategy without duplication. `phase_1_research_read` is synthesized from linked observations; none of them ever feed the Phase 3 response gate, and their raw text never leaves the protected research views.
  - **Classifications are a second table, not a field** (round-4): `research_observation_classifications`, many rows per observation, one per taxonomy and version (`venture-schema-contract.md` §5.4c). Each venture stamps one taxonomy and its links name the classification they use, so two ventures can read the same corpus under different label sets without either duplicating the text or seeing the other's labels. Re-classifying writes a classification row, never a second observation.
- **`phase-N-<name>/`** — that phase's working drafts (post ideas, lead magnet copy, landing page copy blocks, product outline), parallel to how `/atomize` produces `content/<slug>/derivatives/`.

### D. Review loop / checkpoint gating

The original plan's "venture phase deliverable" row type can't actually work with the queue as it exists: `src/publish/queue.ts`'s `QueueRow` only has `platform`/`format`/`status`/`notes`/`origin` — no way to say a row isn't meant to publish anywhere, or which checkpoint it belongs to. The review app compounds this: `src/review/rows.ts` recognizes exactly five `kind`s (text/image/video/storyboard/outreach-message), discovers rows only from two roots (`content/` and `outreach/leads/`), and `saveDerivative`/`enrich` assume an editable body lives at `derivatives/<id>.md`. Landing-page copy, surveys, welcome emails, a product outline, and thank-you notes don't fit any of that — they'd become rows the app can't render or edit correctly, not harmless new rows.

**The concrete contract for everything in this section — exact field names, enum values, who writes each field, both state machines with their allowed transitions and actors, the per-artifact-kind matrix, evidence shapes, the checkpoint read model the GUI renders, and the legacy-row mapping — is in `docs/venture-schema-contract.md`. Design and build against that document; this section is the summary.**

This build needs the queue schema extended with:

- `artifact_kind` — e.g. `substack-post` (renamed from the earlier `text-post-longform` — a sub-150-word Starter Kit post is not "long-form"; see §F and `venture-schema-contract.md` §3), `text-post-note`, `landing-page-copy`, `welcome-email`, `survey`, `product-outline`, `price-decision`, `thank-you-note`.
- `publishable` — explicit boolean. Publishers (Typefully, the Substack agent, `ready-to-paste`) must check this is `true`, never infer it from `platform`/`format` the way they do today.
- `checkpoint_id` — which phase checkpoint this row counts toward (e.g. `checkpoint-1`).
- `editorial_status` and `delivery_status` — the two independent state machines from Model notes, replacing the single `status` column for venture rows (existing atomize/outreach rows keep `status` as-is; this is additive, not a breaking rename).
- `evidence` — what proves delivery: a URL, a provider reference, or a human attestation string.

`src/review/rows.ts` needs: the new `artifact_kind`s added to its `Kind` type and `enrich()`; `venture/<slug>/phase-N-*/` added as a third discovery root alongside `CONTENT`/`OUTREACH_LEADS`; and an editable-body path that isn't hardcoded to `derivatives/<id>.md` for venture artifacts. Publishers must require `publishable=true` before acting on a row — not infer it from platform, the way `publishText` currently filters on `TEXT_PLATFORMS` membership alone.

## F. The rules contract — `venture/rules.md` (authority) and `venture/rules.yaml` (runtime input)

**This exists now.** `venture/rules.md` is a drafted, versioned, normative specification distilled from the PDF and the Welsh note, with the civic-tech worked example deliberately excluded (it lives separately as a fixture — see below). It is a required build artifact, not a "nice to have if there's time" note. Current version: `venture-rules-2026-08-07-draft-1`, status **draft, awaiting Muxin's approval** — it is documentation, and Work package 1 (this rebase) stops short of implementing anything against it.

**What it is.** The human-readable, normative source of truth for: the four phases and their day ranges; the operating rules (sequence, context, calendar, copy blocks); content and voice standards; the post writing order; the full 25-question intake plus voice-evidence and Day 14 scorecard requirements; Phase 1's platform-recommendation and ten-idea-ranking rubrics; Phase 2's five-concept lead-magnet rubric and Checkpoint 2's proposed predicate; Phase 3's response record shape, the response-gate/phase-3-completion split, the six-factor problem score, and the pricing method; Phase 4's daily-plan adaptation, triage, automation order, and Day 14 scorecard/decision; decision-record and privacy requirements; and the user-facing copy substitution table.

**What it is not, and this must stay explicit everywhere it's referenced.** `venture/rules.md` does not execute. It does not load itself, choose a platform, select a CTA, enforce a gate, or make any phase script follow the Starter Kit on its own. Creating or editing this file is documentation work. Nothing reads Markdown prose at runtime — see the concrete decision below for what a phase script actually loads.

**`venture/rules.yaml` is a required runtime input, not an optional companion.** Three runtime-loading stories were once open — parse the Markdown prose directly, write a YAML companion, or go straight to a hand-written typed config — which made "what does a phase script actually read at midnight" unanswerable. Decided: Work package 2 MUST author `venture/rules.yaml` as the sole machine-readable source a phase script loads — thresholds, rubrics, stage policies, required-output lists, gate predicates, the CTA-by-phase table, and the artifact-kind list, all as structured data, no prose parsing. `venture/rules.md` remains the explanation and the authority for *what the rules mean and why*; a human resolves any dispute by reading the Markdown, never the YAML. Concretely:

- `src/venture/rules.ts` (§ Files) loads `venture/rules.yaml` only, never `venture/rules.md`, at runtime;
- a **parity check** (test, named in Model notes below) asserts every threshold, enum, and gate predicate in `venture/rules.yaml` matches what `venture/rules.md`'s prose currently states — this is what stops the two files from silently drifting apart, which plain "keep them in sync" prose can't enforce;
- both files carry the same rules-version string; a version mismatch between the YAML a running venture was stamped with and the YAML currently in the repo fails the phase script clearly, per the version-stamping rule below — this was already required for `venture/rules.md`'s version, and now applies to the YAML specifically, since that's what's actually loaded;
- `venture/rules.yaml` does not exist yet — authoring it, plus the parity test and the `rules.ts` loader, is Work package 2's job, not this documentation pass's.

**Version stamping.** Every venture records `venture/rules.md`'s rules-version string and both source hashes (PDF, Welsh note) in `canon.md` at kickoff (§B), and every `decisions.jsonl` entry (§D, `venture-schema-contract.md`) carries the rules-version it was made under. A rules revision after a venture has started does not retroactively change that venture's stamped version.

**The civic-tech fixture stays a fixture.** If an example is useful anywhere in this build (tests, onboarding a new contributor, illustrating what a filled-in venture looks like), it belongs in a clearly separate file such as `venture/examples/civic-tech-worked-example.md` — never inline in `rules.md`, never ingested by a phase script's runtime context. §D's clean-fixture test (see Model notes) is what proves this boundary holds.

## Model notes / guardrails

- **Editorial and delivery are two separate state machines, not one `status` column.** Editorial: `draft → approved | discarded`. Delivery: `not_applicable | ready → scheduled → live_confirmed | failed`. Checkpoints reference a manifest of required artifact IDs and require evidence appropriate to each: a public URL (Substack essay), an agent-confirmed post (Notes), or an explicit human attestation (anything with no other verifiable trace). This replaces the original plan's "verify all rows are `approve`d" checkpoint criteria, which conflated Muxin's editorial decision with the post actually being live — Typefully in particular flips a row to `published` the moment it creates a *scheduled* draft, which proves nothing about it being publicly live yet.
- **Checkpoint transitions must be idempotent and crash-safe.** Fiction's `canon.ts` blindly appends to `canon.md` on every invocation with no duplicate-transition guard — fine for a human manually locking one chapter at a time, too weak for a scripted multi-phase gate. Use deterministic checkpoint event IDs (e.g. `venture-slug/checkpoint-2`), reject a transition whose id has already been recorded, and order the writes so a crash mid-transition can't leave contradictory state — write the `canon.md` entry first, only flip `state.md`'s phase/checkpoint fields after, so a crash before that second write just looks like "not yet advanced" and is safely re-run. Derive current state from the event ledger where possible instead of trusting a separately-maintained flag.
- **The Phase 3 response gate has a privacy-sensitive data model, not just a count.** Keep `responses.jsonl` out of git entirely (same treatment as `data/analytics.db`) — it can hold raw email/DM/comment text and identifying detail. Each entry redacts identity to a respondent hash, not a name or email. `canon.md` only ever gets the aggregate count plus a redacted synthesis. The ≥20 gate counts ELIGIBLE UNIQUE responses — a script dedupes by respondent hash and checks target-audience eligibility, it does not just count rows or messages pasted in.
- **The response gate is scoped to the problem/outline/price steps specifically, not the whole of Phase 3, and it is a different event from Phase 3 completing.** The source framework's own restriction is "do not identify the problem, outline the product, or price it until you have enough data" — posting ("keep the engine running") is explicitly allowed to continue in parallel below 20 responses. Use two distinct, separately-recorded events (`venture/rules.md` §7.3, §7.10): `response_gate_opened` at ≥20 eligible unique respondents, which unlocks cluster/problem/outline/price *analysis* only, and `phase_3_completed`, which requires problem, transformation, outline, price, and pitch all editorially approved and is what actually unlocks Phase 4. The earlier draft of this plan and `venture-schema-contract.md` both called the response threshold "Checkpoint 3" and let it read as unlocking Phase 4 directly — that conflation is exactly what the 2026-08-07 audit flagged and what this revision corrects. `venture:checkpoint` should block only the analysis/outline/price actions below the gate, never posting.
- **`venture/rules.md` is the authority; `venture/rules.yaml` is the runtime input — see §F.** They distill the PDF and the Welsh note, exclude the civic-tech worked example and its $49 price by design, and are both required build artifacts as of the corrective pass. What remains for Work package 2 is authoring the YAML, writing and testing the runtime reader (`src/venture/rules.ts`) that loads it, validating the stamped version, and the parity check that keeps the YAML and the Markdown from drifting apart — not producing the Markdown document itself.
- **Phase 1 is a research phase with three distinct artifacts, and Checkpoint 1 clearing does not by itself mean anything was learned.** A reviewed `phase_1_research_plan` gates idea drafting; posting three approved, live posts (Checkpoint 1) is necessary but not sufficient; a rubric-backed `phase_1_research_read`, itself reviewed by Muxin, then feeds a `phase-1-research-continuation` decision (`more_probes` / `proceed_with_evidence` / `proceed_as_hypothesis`) before `venture:phase2` may run. Evidence for the read comes from every signal channel via the account-level `research_observations` store (Substack metrics, essay comments, Note replies, DMs, emails, subscriber movement, follow-up questions, creator observations), linked into this venture with a derived `evidence_role`, never from one engagement number alone. See `venture/rules.md` §5.1A/§5.2/§5.6, `venture-schema-contract.md` §2C/§5.4a/§5.4b.
- **The research read can surface what nobody planned for, and existing Substack history counts as evidence — added round-2 corrective pass.** A finding is `planned` (traces to an unknown the plan already named) or `emergent` (something the observations turned up that nobody anticipated); an emergent finding needs Muxin's explicit yes/no before it can shape Phase 2, since nothing in the plan already vetted it. Separately, Notes/comments/metrics/subscriber data from before this venture's Phase 1 began are first-class evidence too — they can populate `confirmed_knowns` and cut down on redundant testing, but they never count toward Checkpoint 1's live-post requirement or the Phase 3 response gate, which stay scoped to this venture's own controlled collection. See `venture/rules.md` §5.6, `venture-schema-contract.md` §2C.3/§5.4b.
- **Evidence is account-level; only the judgments about it are per-venture — round-3, refined round-4.** `research_observations` (a table in the existing gitignored `data/analytics.db`) holds each observation once, account-wide. Its classifications live in a companion `research_observation_classifications` table, many per observation, one per taxonomy and version — topic labels, emotional frame, desired help, behavior role, stuck point, each with confidence, an evidence span, and the option to abstain rather than guess. Each venture's `evidence-links.jsonl` names the classification it uses and adds what only makes sense relative to *that* venture: `evidence_role`, `unknown_ids`, `target_audience_fit`, and the `research_plan_version` those unknowns were assigned under. **`evidence_role` is derived, never declared by a collector** — published before kickoff → `historical_prior`; otherwise one of this venture's registered probes → `current_probe`; otherwise → `current_organic` — so the same reply reads differently for two ventures with different start dates, and re-running ingestion during a live sprint can't mislabel fresh probe replies as history. Signals and `/strategy` read the account-level store through its redacted read path and never open a file under `venture/`. See `venture-schema-contract.md` §5.4a/§5.4b.
- **Signals reads four separate outcome families from existing records, not a fifth one.** Attention (views), conversation (replies/comments/likes/restacks/saves), audience (visits/opt-ins/subscribers), and business (qualified inquiries/calls/opportunities/purchases) are named in `content-studio-vision.md`'s Signals section and now formally mapped to `signal-snapshot` and `funnel-events.jsonl` fields in `venture-schema-contract.md` §5.8 — grouped at render time, never averaged into one score. A pillar/platform-suppression recommendation may read attention and conversation, never audience or business, so a low-reach post that converted isn't misread as underperforming.
  - **Current state, corrected round-4:** `/strategy` reads `data/analytics.db` and writes a dated brief; **Signals reads that brief** (`src/review/signals.ts`'s `readSignals()` parses `briefs/<date>-strategy-brief.md`), not the database. An earlier draft claimed Signals already read `analytics.db` — it does not. Adding the redacted research-observation read to Signals is new work, tracked as Card D in the backlog proposal.
- **Every judgment step needs a decision record, not just a delivery artifact.** Platform recommendation, the ten ranked ideas (including which `unknown_id` each selected idea probes — distinct-unknown coverage, `venture/rules.md` §5.2, `venture-schema-contract.md` §2C.5), the `phase-1-research-continuation` call, the five lead-magnet concepts, response clustering and problem selection, the transformation choice, product format and price, and the Day 14 continue/revise/stop call all get a `decisions.jsonl` entry: candidates, per-candidate scores, evidence references, the AI's recommendation and rationale, Muxin's selection, the selecting actor, an override reason when she picks something else, and the rules version the decision was made under. See `venture-schema-contract.md` for the field shape. This is what makes "why did the system recommend this" answerable after the fact, and it's what a "show your reasoning" / "choose another" control in the UI would read from.
- **The 14-day clock needs more than a day counter.** Track planned phase-day, elapsed calendar day, active-work day, and "blocked waiting on Phase 3 responses" as separate fields. A missed Day 14 should reschedule downstream milestones — it must never silently advance a phase or manufacture validation just to hit the date.
- **"Validated content engine" needs a ship predicate defined at intake, not invented at Day 14.** Fix the scorecard when `intake.md` is written: live post count, qualified views/clicks, opt-in conversion rate, unique eligible response count, a response-quality read (not just the count), and a sustainability check (can Muxin actually keep the daily checklist running). Include explicit failure branches — revise positioning or the lead magnet — not just a path that proceeds straight to product. Full field list: `venture/rules.md` §4.4.
- **Phase 4's daily plan must adapt to the time budget fixed at intake, not assume 2h15m.** If question 20's answer is below the PDF's canonical 2-hour-15-minute routine, offer a recorded choice — use the canonical routine, rotate the five jobs across the week, extend the timeline, or revise pace/scope — rather than presenting an unsustainable routine as the plan. Full rule: `venture/rules.md` §8.1.
- **`npm run check` (typechecking only) is not enough verification for this build.** Stage 0 (`docs/maturity.md`) justifies skipping CI infrastructure, not skipping behavioral tests for safety-critical gates. At minimum, add tests for: allowed/rejected editorial and delivery state transitions; checkpoint idempotency, including an interrupted write between the `canon.md` and `state.md` steps; response eligibility and dedup logic; venture-root discovery and path-traversal safety (mirrors the slug-injection guard `safeFolder` already has in `rows.ts`); non-`publishable` artifacts being excluded from every publish path; compatibility with legacy queue rows that carry none of the new schema fields; **fixture isolation** — a freshly-scaffolded, non-civic venture must contain zero civic terms, zero fixed cluster weights, zero preselected $49 price, and a `phase_1_research_read` whose emotional-frame/audience-segment categories never match the civic-tech fixture's, verified by asserting the phase-1/phase-2/phase-3 runtime context never includes the `venture/examples/` fixture path; **decision-record integrity** — every judgment step actually writes a `decisions.jsonl` entry with the fields above, and a checkpoint/gate reader derives state from `canon.md`'s ledger rather than trusting a separately-maintained flag; **rules parity** — a test asserts `venture/rules.yaml`'s thresholds, enums, and gate predicates match what `venture/rules.md`'s prose currently states (§F), so the two files can't silently drift; **Phase 1 research gating** — a test drives a clean venture's `phase_1_research_plan` through drafted-but-unreviewed and confirms idea drafting is rejected, then confirms it's allowed once `reviewed_by_muxin` is true, and separately confirms Phase 2 concept generation is rejected while the `phase-1-research-continuation` decision is unselected or `more_probes`, and allowed once it's `selected` with `proceed_with_evidence` or `proceed_as_hypothesis`; **emergent-finding confirmation** — an emergent finding is excluded from `lead_magnet_implications` until `muxin_confirmed_emergent` is set, per `venture-schema-contract.md` §9 item 8; **historical-evidence non-gating** — `historical_prior`-tagged observations never move Checkpoint 1 or the Phase 3 response-gate count, per §9 item 9; and **rubric and attribution completeness** — a `signal_quality` label always has all eight rationale factors scored, and a funnel attribution entry never has both or neither of `content_item_id`/`unattributed_reason` set, per §9 items 10–11.
- **One venture at a time is fine for v1.** Multiple concurrent `venture/<slug>/` folders should work structurally (same pattern as multiple `stories/<slug>/` series) but don't need to be a design target until there's a second venture.
